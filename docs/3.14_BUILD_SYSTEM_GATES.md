# ASMPython 3.14 advanced build-system gates

This document extends `docs/3.14_COMPLETION_GATES.md`; it does not replace the
normative `release-requirements.md` contract.

## Project configuration and target identity

Completion requires:

- automatic, deterministic `build.config.toml` discovery,
- explicit `--config` and `--no-config` behavior,
- CLI values overriding profiles and config predictably,
- a three-part platform/system/ABI target contract,
- the complete normalized triple passed to every backend and linker,
- target triples represented in lockfiles, reports, cache keys, manifests, and
  artifact metadata,
- migration compatibility for older OS-only targets without losing the full
  target identity.

## Build-plan inspection

`asmpython build --graphonly` must perform every non-code-generating preflight
step and report:

- discovered source and import dependencies,
- native/PyinBin partition stages,
- frontend and optimization stages,
- effective backend and linker,
- required and optional component dependencies,
- FastComp cache state,
- runtime and embedded resources,
- bundling, verification, signing, and output stages.

Text, schema-versioned JSON, and Graphviz DOT output must be deterministic.
Graph-only mode must not invoke assembly, code generation, linking, or publish
an artifact.

## Deep FastComp state

The incremental compilation gate is incomplete until FastComp can safely reuse:

- parsed modules,
- semantic-analysis products,
- dependency graphs and hashes,
- typed and optimized IR,
- serializable backend state,
- object fragments and linker inputs,
- resource manifests and debugger metadata.

Every cache layer must include compiler version, target triple, backend/linker
identity and version, effective build policy, extension hashes, and relevant
toolchain identity. A clean build and a fully cached build must be behaviorally
and, where promised, byte-for-byte equivalent.

## Embedded resources

Completion requires:

- deterministic appended resource containers for supported native executable
  and library formats,
- path traversal and duplicate-path rejection,
- per-file and container integrity checks,
- replacement rather than repeated suffix stacking,
- ordinary mapping access through `from asmpython import embedded`,
- nested directory dictionaries and lossless byte leaves,
- compatibility with signing, lockfiles, FastComp, build reports, and artifact
  verification,
- tests proving platform loaders ignore the appended suffix.

## Debugger integration

Completion requires:

- backend/linker debug-format capability negotiation,
- real DWARF, PDB/CodeView, or source-map emission on every target claiming it,
- source lines, functions, in-scope variables, and optimized-out diagnostics,
- coherent native/PyinBin stack navigation,
- debugger adapters or documented workflows for GDB, LLDB, and WinDbg,
- debug metadata included in lockfiles, reports, cache keys, and artifact
  verification,
- loud failure instead of silently producing a non-debuggable artifact.

## Artifact verification

Completion requires structural and integrity verification for every claimed
artifact format, including:

- architecture and target identity,
- executable/container header validity,
- exported/imported symbols where applicable,
- appended resources,
- ABI manifests,
- detached signatures and certificate metadata,
- debug sidecars,
- build-lock and manifest agreement.

A produced artifact that fails verification must not replace a previous valid
output or be presented as a successful build.

## Release rule

These gates may be implemented without altering Python syntax or semantics.
ASMPython 3.14 must not claim them as complete while frontend/backend state is
only warmed but never consumed, debugger files contain only placeholders, or
artifact checks validate only file magic without target-specific execution or
independent tooling.
