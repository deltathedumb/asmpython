# ASMPython 3.14 completion gates

This checklist condenses the existing `release-requirements.md` contract into the
ten release-defining workstreams that must be completed before the Python 3.14
release line can be declared production-ready. It is a navigation and execution
checklist; `release-requirements.md` remains the normative source of truth.

The canonical full release identity uses:

```text
<python-language-version>-<asmpython-semver>
```

The current planned release is `3.14-2.0.0`.

## 1. Finished Python correctness

ASMPython must correctly implement ordinary Python 3.14 behavior across the
native compiler, PyinBin, and hybrid execution. Completion requires:

- complete Python 3.14 parsing and semantic analysis,
- closure and `nonlocal` correctness,
- descriptors, metaclasses, exceptions, generators, coroutines, pattern
  matching, annotations, imports, reflection, and dynamic compilation,
- correct arbitrary-precision and object semantics rather than silent fixed-size
  approximations,
- all known native and PyinBin regressions resolved or precisely rejected,
- full differential conformance runs against CPython 3.14,
- no known silent miscompilation or silent semantic deviation.

## 2. Global memory-runtime adoption

The shared ownership runtime must become the single lifetime model used by:

- x86-64 generated code,
- ARM64 generated code,
- PyinBin values and frames,
- native/PyinBin bridge objects,
- FFI values and callbacks,
- PortaPy runtime and value handles.

Completion requires correct retain/release behavior, borrowed and transferred
references, tracing and cycle collection, weak references, finalizers,
generator/coroutine cleanup, deterministic runtime teardown, and leak/use-after-
free/double-free stress testing. A Python reference implementation alone does
not complete this gate; native allocations must use the same ownership ABI.

## 3. Hybrid execution

The compiler must automatically partition programs between native execution and
PyinBin without requiring manual source rewrites. Completion requires:

- native to PyinBin calls,
- PyinBin to native calls,
- callbacks and re-entry in both directions,
- shared identity, aliasing, mutation, class identity, iteration state, and
  cyclic references,
- exception type, message, cause, context, and traceback preservation,
- coherent mixed native/PyinBin tracebacks,
- automatic packaging of required interpreted code in normal builds,
- inspector visibility for every inserted boundary and its reason.

## 4. Finished core CLI

The stable core command family must include:

```text
asmpython build
asmpython run
asmpython check
asmpython inspect
asmpython test
asmpython doctor
asmpython explain
asmpython version
asmpython backends
asmpython ir
asmpython cache
asmpython profile
```

The retired `asmpython irbuild` and `asmpython invalidate` commands must remain
clear migration errors pointing to `asmpython ir` and `asmpython cache clear`.

Every command must have stable exit codes, human-readable and machine-readable
output where applicable, Unicode/path correctness, actionable diagnostics,
atomic output replacement, and no implementation-language traceback for normal
user errors.

## 5. Finished standard-library and package support

Every public Python 3.14 standard-library module must be classified as fully
compatible, native-service-backed, PyinBin-backed, platform-inapplicable, or
intentionally unsupported with a documented reason. No public module may remain
uncategorized.

Normal Python packaging must work through ordinary `pip` environments and
`site-packages`, including:

- pure-Python packages,
- relative and namespace packages,
- wheels and package data,
- `importlib.resources`,
- entry points and metadata,
- optional dependencies and environment markers,
- precise detection and reporting of CPython-specific native extensions,
- a documented Stable-ABI/`abi3` compatibility boundary.

The compatibility scourer and `asmpython test` must publish exact four-engine
results for CPython, native, PyinBin, and hybrid execution.

## 6. Finish PortaPy — parallel effort

PortaPy is a parallel workstream currently in progress. It must remain a
separately versioned embeddable product built from the reusable Python-authored
interpreter core shared with PyinBin.

Completion requires:

- a standalone project/repository rather than an internal import of
  `asmpython.pyinbin`,
- `portapy.dll`, `libportapy.so`, and `libportapy.dylib`,
- a stable opaque-handle C ABI,
- source execution, evaluation, calls, conversions, imports, bytecode loading,
  host callbacks, interruption, and structured errors,
- shared ownership semantics with the global memory runtime,
- conformance from C and at least one additional host language,
- ABI v1 stabilization only after cross-platform host verification.

PortaPy development proceeds in parallel with compiler work; routine compiler
progress must not pause merely because the PortaPy workstream is still active.
The companion PortaPy release remains part of the complete 3.14 platform claim.

## 7. Release engineering

The release must be supported by reproducible evidence rather than feature
claims. Completion requires:

- deterministic clean and incremental builds,
- byte-identical FastComp and clean-build outputs where promised,
- self-hosting measurement and reproducibility verification,
- complete x86-64, ARM64, PyinBin, and hybrid regression matrices,
- real-platform or independently validated emulator execution,
- benchmarks with committed methodology and regression thresholds,
- build manifests, checksums, SBOMs, and provenance,
- signed and validated release artifacts,
- installation, upgrade, rollback, and uninstall testing,
- release notes and migration documentation,
- no stale version references conflicting with `3.14-2.0.0`,
- a final release audit proving every gate above is complete.

## 8. Fast compile / lower-quality output mode

`asmpython build ... --speedy-lossy` must be a real end-to-end build policy. It
prioritizes compiler and linker latency while explicitly permitting slower,
larger, or less optimized generated programs. It must never permit incorrect
program behavior.

Completion requires:

- a concrete `speedy_lossy: bool` passed to every backend compile call,
- the same value passed to every backend link call and standalone linker context,
- backend- and linker-specific freedom to choose cheaper algorithms,
- skipped or reduced expensive optimization passes where safe,
- build output that clearly states the mode and its expected performance costs,
- manifests/cache keys that record the mode so normal and lossy artifacts never
  collide,
- tests proving both `True` and `False` are always passed explicitly,
- no claim that speedy-lossy artifacts represent release-performance results.

## 9. Native libraries, ABI, and FFI

ASMPython must produce native libraries that ordinary external programs can call
without embedding CPython or depending on ASMPython-specific process state.

Completion requires:

- shared libraries, static libraries, object files, and platform import libraries,
- stable exported symbol names and visibility rules,
- generated C headers or equivalent machine-readable ABI manifests,
- platform calling conventions and explicit ABI selection,
- primitive values, strings, buffers, structs, opaque handles, and callbacks,
- ownership/lifetime annotations integrated with the global memory runtime,
- structured errors that do not unwind Python exceptions through foreign frames,
- native-to-Python and Python-to-native calls with re-entry and thread safety,
- ABI compatibility tests from C and at least one additional language,
- versioned ABI compatibility and deliberate breakage rules.

## 10. Developer tooling and toolchain status

The release must provide tooling that explains what the compiler did rather than
forcing users to infer it from generated binaries or internal tracebacks.

Completion requires:

- `asmpython inspect` reports for native/PyinBin partitioning, allocations,
  boxing, boundaries, slow paths, imports, and unsupported behavior,
- `asmpython doctor` validation for compilers, linkers, SDKs, runtimes, caches,
  target support, and environment configuration,
- optimization, code-size, allocation, and compile-time reports,
- source-level debug metadata for GDB, LLDB, and WinDbg where supported,
- compiler crash bundles with sanitized source/IR/toolchain metadata,
- stable JSON and SARIF diagnostics with documented error codes,
- explicit `production_suitable` metadata for every backend and linker,
- visible warnings whenever a non-production backend or linker is selected,
- backend/linker discovery output that distinguishes scaffold, experimental,
  preview, legacy, and production components.

## Release rule

ASMPython 3.14 must not be called complete while any gate above is satisfied only
by scaffolding, a happy-path test, a host-Python reference implementation, or an
unverified compatibility claim. Experimental backend scaffolds may ship as
visible placeholders, but they are excluded from production support claims.
