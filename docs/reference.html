Non-standard builtins #

Most of asmpython's built-in functions behave exactly like CPython's (len, print, range, sorted, etc.) — see the CPython builtins docs for those. This table covers only the builtins that are asmpython-specific additions, or where asmpython's behavior differs from or restricts CPython's built-in of the same name.

FunctionDescription
import_binary(path)asmpython-only. Loads a shared library at runtime (LoadLibraryW/dlopen) and returns a dynamic-module handle; functions are declared against it with @handle.imported. See Dynamic loading.
gl_import()asmpython-only. Like import_binary, but resolves each attached function through SDL_GL_GetProcAddress instead of LoadLibrary/dlsym — the correct lookup path for OpenGL functions beyond GL 1.1. Takes no arguments.
isinstance(obj, cls)Real runtime type check that respects single inheritance, but asmpython has no multiple inheritance and no metaclasses — isinstance can only ever check against the single static inheritance chain the compiler already knows about, not arbitrary runtime-registered ABCs.
hasattr(obj, name) / getattr(obj, name, default) / setattr(obj, name, val)Attribute access is otherwise CPython-shaped, but asmpython has no dynamic attribute creation — every instance attribute must already have been assigned somewhere in __init__, so these three cannot be used to add a genuinely new attribute name to an instance at runtime.
type(x)Returns a <class 'T'>-style string, not a first-class type object — asmpython has no metaclasses, and type()/__class__ are read-only.
hash(x)Same contract as CPython's hash, but the concrete algorithm is fixed and asmpython-specific: strings hash via FNV-1a (not CPython's randomized SipHash), so hash values are not compatible with CPython's for the same string, and are stable/non-randomized across runs of the same binary.

Error codes #

Every diagnostic carries a stable code: L0xx for lex errors, P0xx for parse errors, E0xx for semantic errors. Run asmpython --explain <CODE> for the full description of any code.

Display format

The code tag (e.g. [E001]) is always shown in brackets, and --explain CODE lookups always work, regardless of display format. But the text in front of the code tag now varies by code:

  • Lex and parse errors (all L0xx/P0xx) always display as SyntaxError, mirroring CPython's own tokenizer/parser diagnostics.
  • Semantic errors (E0xx) with a real CPython exception equivalent display using that exception's class name. For example, a name-resolution failure now reads NameError: [E001] name 'x' is not defined instead of the old semantic error: [E001] ... wording.
  • A handful of E0xx codes have no CPython equivalent and keep the old generic "{phase} error" wording (i.e. semantic error: [E0xx] ...): E003/E004 (function/class redefined in the same scope — CPython allows silent redefinition, so there's no matching exception), the asmpython-only concepts E061–E063 (assembly-directive errors), and every compiler-extension diagnostic (E081–E093) — access/final/sealed/enum/immutable/exhaustive_switch are all asmpython-specific concepts with no real CPython exception to map onto.
output
broken.py:3:5: NameError: [E001] name 'greet' is not defined
  greet("world")
  ^

The source of truth for the code → exception-name mapping is _PYTHON_EXCEPTION_NAME and _python_exception_name() in asmpython/_compiler/errors.py.

Limitations #

  • No bignum — integers are 64-bit signed; overflow wraps
  • Homogeneous lists — list[T] requires all elements to be the same type; list (bare) allows any
  • String keys only — dict and set elements must be strings (runtime limitation)
  • Single inheritance — multiple inheritance is not supported
  • No metaclasses — type() and __class__ are read-only
  • No dynamic attribute creation — all instance attributes must be assigned in __init__
  • No mapping patterns in match/case
  • Generator expressions are eager — (x for x in xs) materializes immediately
  • *expr unpacking at call sites requires a statically-known tuple (literal or named variable)
  • No async/await — asyncio ships as a subset of primitives, not a real event loop
  • No real TLS/SQLite — ssl and sqlite3 are API-shaped stubs pending a C library binding
  • No runtime introspection beyond isinstance, hasattr, getattr, type
  • @assembly_func requires --backend legacy — the x86-64 IR backend has no raw-NASM escape hatch
  • The x86-64 backend supports windows/linux only — freestanding/freestanding16 and ARM64/macOS/Raspberry Pi targets still need the legacy backend or don't exist yet; see Backends: legacy & x86-64
  • The builtin linker can't yet parse gcc's bigobj COFF output — asmpython.mlang currently requires --linker gcc; see asmpython.mlang
Most limitations are by design to keep the compiler single-pass and the output zero-overhead. The subset covers a wide range of real programs — see examples/ in the repository for demonstrations.
