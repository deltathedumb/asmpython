Inline assembly #

python
from asmpython.assembly import assembly_func

@assembly_func
def popcnt(x: int) -> int:
    """
    popcnt rax, rdi     ; SysV: x in rdi
    ret
    """

The docstring is raw NASM emitted verbatim as the function body. Arguments arrive in the platform's integer-argument registers (Win64: rcx/rdx/r8/r9; SysV/Linux: rdi/rsi/rdx/rcx/r8/r9).

@assembly_func is only supported by --backend legacy — the x86-64 IR backend has no raw-NASM escape hatch. A program using @assembly_func needs --backend legacy explicitly (or must target a freestanding platform, which selects it automatically). See Backends: legacy & x86-64.

Asm blocks inside a normal function

python
def rdtsc() -> int:
    asm {
        rdtsc
        shl rdx, 32
        or  rax, rdx
    }

Raw NASM inserted verbatim into the function body. The enclosing function's prologue/epilogue is still emitted; the asm block appears between them. Useful for instructions without Python-level wrappers, without giving up the rest of the function to hand-written assembly.

Assembly builder class #

from asmpython.assembly import Assembly gives a chainable builder for generating NASM programmatically — useful for code generators, JITs-within-the-compiled-binary, or any case where the instruction sequence isn't known until runtime.

python
from asmpython.assembly import Assembly

a = Assembly()
a.mov("rax", 0).xor("rbx", "rbx").label("loop").inc("rax").dec("rbx").jnz("loop").ret()
print(a.emit())

150+ instruction methods: full integer ALU, SSE/AVX, atomics, system calls, and the full NASM directive set. Each method appends one formatted line to the builder's internal body and returns self for chaining.

Inline FFI #

python
from asmpython._ffi import include, link, extern

include("windows.h")
link("kernel32")

@extern
def GetTickCount() -> int: ...

@extern
def MessageBoxA(hwnd: int, text: str, cap: str, utype: int) -> int: ...

@extern declares a foreign function; the compiler emits an extern NASM directive and routes calls through the platform ABI. include() and link() add #include and -l flags to the compile step. This is compile-time/link-time binding — the symbol must be resolvable by the linker. For a library whose name isn't known until runtime, see import_binary. For embedding real C/C++ source directly (rather than binding to a symbol that already exists in a library), see asmpython.mlang.

Dynamic loading (import_binary) #

Loads a shared library at runtime (a real LoadLibraryW/dlopen handle), as opposed to @extern's compile-time/link-time binding. Functions are declared with @<handle>.imported and resolved via GetProcAddress/dlsym the first time they're called.

python
import sys
from asmpython import import_binary

if sys.platform == "win32":
    libc = import_binary("msvcrt.dll")
else:
    libc = import_binary("libc.so.6")

@libc.imported
def toupper(x: int) -> int: ...

print(libc.toupper(97))   # 65

Only scalar (int/float/str-as-pointer) parameters are supported — the foreign function's real signature isn't introspectable, so the stub's own annotations are the contract. Useful when the library to load isn't known until runtime (plugins, optional dependencies, platform-specific DLLs picked by name).

asmpython.mlang #

Embeds another language's source directly in your asmpython program and calls into it, compiled by a real external compiler as part of the asmpython build — not @extern's bind-to-an- existing-symbol model, and not import_binary's runtime dlopen model. mlang compiles source text you write inline.

This all happens at asmpython build time: the configured compiler (e.g. g++) runs once, as a real step of python -m asmpython, and its output object file is linked into your binary. There is no runtime compiler dependency in the produced executable, and nothing about mlang executes when your compiled program runs — by the time you have a binary, the embedded source is long gone, replaced by native code.

Basic usage

python
import asmpython.mlang as ml

code = ml.Code(
    ml.builtins.gcc.cpp,
    'extern "C" int add(int a, int b) { return a + b; }',
)

print(code.add(1, 2))   # 3

Exported functions become callable directly as attributes on the Code object — code.add(1, 2) above. Under plain CPython (e.g. running the source file directly instead of compiling it), Code/Config are inert data holders: no compiler runs, and calling an exported function raises RuntimeError instead. The real compiler invocation, signature inference, and call marshaling only happen inside the asmpython compiler itself, when it recognizes an asmpython.mlang import and a Code(...) construction in the source being compiled.

ml.Config

Config(exe, frontend, compile_args, infer_signatures=False) describes one compiler toolchain:

FieldMeaning
exeThe compiler executable — found on PATH, or an absolute path
frontendShort label for the source language/dialect (e.g. "cpp", "c", "rust") — descriptive, and the dispatch key infer_signatures uses to pick its restricted-grammar parser (C/C++-family or Rust today — see below)
compile_argsargv template compiling one source file to one object file, with {src}/{out} substituted for real temp-file paths
infer_signaturesWhether Code(...) may omit exports= and rely on a source-text scan instead — only meaningful for "cpp"/"c"/"rust" frontends today

Example custom Config for a compiler with no built-in (a cross-compiler, a non-default toolchain, a language not listed below):

python
zig = ml.Config(
    exe="zig",
    frontend="zig",
    compile_args=["build-obj", "-femit-bin={out}", "{src}"],
)   # infer_signatures defaults to False -- "zig" isn't a recognized
    # inference frontend, so every Code(...) using this Config needs
    # an explicit exports=

Built-in configs

ml.builtins.gcc.cpp / ml.builtins.gcc.c are ready-made Configs for a real g++/gcc found on PATH. ml.builtins.rust is the same for rustc (compiling to a staticlib object with -C panic=abort — plain Rust panic-unwinding symbols aren't resolvable from a bare staticlib build, confirmed via a real link failure without it). All three set infer_signatures=True: C/C++ functions are recognized from a plain TYPE NAME(TYPE, ...) { ... } shape, Rust functions from #[no_mangle] pub extern "C" fn NAME(...) -> TYPE { ... } (a separate grammar — Rust's syntax doesn't match the C-family one at all).

ml.builtins.nasm.win64 / ml.builtins.nasm.elf64 wrap raw nasm, one Config per object format — there's no single ml.builtins.nasm, since -f win64/-f elf64 aren't interchangeable and Config resolves fully at compile time with no notion of the build's eventual target OS. Both set infer_signatures=False (raw NASM has no function-signature syntax to scan for at all) — every Code(...) using either needs an explicit exports=. See Built-in mlang configs for the full table and a worked NASM example.

C# and Java are deliberately not built in — both only produce a genuinely linkable object via ahead-of-time native compilation, and neither AOT toolchain fits mlang's model cleanly today (GraalVM's native-image has no object-only output mode at all; .NET Native AOT's object depends on MSVC-format runtime libraries that don't reliably cross-link with asmpython's GNU-toolchain-based linkers). See Built-in mlang configs for the full writeup.

Signature inference

When a Config opts in via infer_signatures=True (true for every built-in ml.builtins.* config), Code(config, source) can omit exports= entirely. Inference parses a deliberately restricted C-family function-signature grammar directly from the source text — no real C++ parser, no name-demangler: each top-level function is matched against [extern "C"] TYPE NAME(TYPE, TYPE, ...) {, and every matched function is wrapped in extern "C" before compilation (if not already) so the compiled object's symbol name exactly equals the parsed name, with no mangling ambiguity to resolve. Recognized types are int/long/ long long (asmpython int), float/double (asmpython float), and void as a return type only. This only sees plain top-level function definitions — templates, overloads, classes, and anything the restricted grammar doesn't match are invisible to inference and need an explicit exports= entry instead.

Explicit exports and Sig

For a non-inferring Config, or any function the inference grammar can't see, declare each exported function's signature explicitly with Sig(arg_types, ret_type) — the same arg_types/ret_type vocabulary ("int"/"float"/"str") as asmpython.stdlib's own Func:

python
import asmpython.mlang as ml
from asmpython.mlang import Sig

code = ml.Code(
    ml.builtins.gcc.c,
    '''
    int square(int n) { return n * n; }
    ''',
    exports={"square": Sig(["int"], "int")},
)

print(code.square(7))   # 49

Explicit exports entries always win over an inferred signature for the same function name.

Linker requirement

Programs using asmpython.mlang currently require --linker gcc (and the compiler auto-defaults to it when an mlang.Code(...) is detected, unless --linker is passed explicitly). Real g++/gcc output on Windows is a "bigobj" PE-COFF variant that the builtin linker's COFF parser — scoped to what NASM emits — doesn't understand yet. Supporting --linker builtin for real-compiler output needs a real bigobj-format COFF parser, tracked as a known follow-up rather than a quick fix. See Backends: legacy & x86-64 for the full backend/linker relationship.
