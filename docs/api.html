Public API #

The compiled language asmpython accepts is plain Python (see CPython docs). This page is about a different surface: the real Python package you pip install and import on the host interpreter to write build tooling — custom codegen backends, custom linkers, and compiler-syntax extensions. None of this executes inside a compiled asmpython program; it all runs under ordinary CPython, as part of driving a build.

The public surface is namespaced, not flat:

python
import asmpython

asmpython.backend.Backend(name="my_backend", impl=my_backend_impl)
asmpython.linker.Linker(name="my_linker", impl=my_linker_impl)
asmpython.extend.Extension(id="my_ext", statement_handlers={...})
There is no flat asmpython.Backend / asmpython.linker.Linker / asmpython.Extension shorthand and no backwards-compatibility alias for one — asmpython.backend, asmpython.linker, and asmpython.extend are the only public entry points, each a separate submodule imported lazily so a plain import asmpython doesn't pull in the whole compiler frontend.

All three follow the same shape: construct the class, and registration happens immediately as a side effect — there's no separate .register() call. Each registered thing becomes selectable from the CLI (--backend NAME, --linker NAME, --ext NAME) on any later asmpython build invocation in that process, or via a plugin file loaded through --ext path/to/plugin.py.

asmpython.backend

Register a full codegen backend — something that turns a compiled module into object bytes and links them. See below.

asmpython.linker

Register just a linker, reusable by any backend that wants it. See below.

asmpython.extend

Register a new statement-level keyword, handled by your own parser callback. See below.

asmpython.backend #

asmpython.backend.Backend(name, impl) registers a codegen backend, selectable via --backend name.

python
import asmpython

backend = asmpython.backend
backend.Backend(name="my_backend", impl=my_backend_impl)

Then: asmpython build myfile.py --backend my_backend.

The impl contract

impl must conform to asmpython._compiler.ir.IRBackend:

MemberRequiredSignature
compileyes(module, args) -> dict[str, bytes]
linkyes(objects, args) -> dict[str, bytes]
requested_argsnolist[dict] — extra CLI args your backend wants parsed and forwarded
default_linkernostr — linker name used when --linker is omitted

A registered backend is driven with a plain compile-then-link-then-write sequence (the same shape the built-in ternary backend uses) — it does not get the bespoke per-backend wiring that x86-64 has (Win64/SysV ABI shims, runtime object linking, gcc resolution for asmpython.mlang). If your backend needs that kind of target-specific plumbing, you provide it yourself inside compile/link.

Minimal example

python
import asmpython

class MyBackend:
    default_linker = "builtin"

    def compile(self, module, args) -> dict:
        # module: the compiler's typed AST/IR handoff object
        # args:   dict of target_os / abi / any requested_args
        obj_bytes = my_codegen(module, args)
        return {"main": obj_bytes}

    def link(self, objects, args) -> dict:
        exe_bytes = my_link(objects, args)
        return {"out": exe_bytes}

asmpython.backend.Backend(name="my_backend", impl=MyBackend())
Backend/linker registries are plain in-process Python dicts, consulted after the built-in names (legacy/x86-64/ternary). They're CPython-hosted-compilation only and not yet safe under self-hosting — asmpython's self-hosted subset has no first-class module/object values it could store a live backend object in.

asmpython.linker #

asmpython.linker.Linker(name, impl) registers a linker, selectable via --linker name — usable independently of any custom backend, including with the built-in x86-64 backend.

python
import asmpython

linker = asmpython.linker
linker.Linker(name="my_linker", impl=my_linker_impl)

Then: asmpython build myfile.py --linker my_linker.

The impl contract

MemberRequiredSignature
linkyes(ctx: dict) -> bytes
requested_argsnolist[dict]

ctx carries at minimum objects (a list of object-file bytes to link) and target_os.

Minimal example

python
import asmpython

class MyLinker:
    def link(self, ctx: dict) -> bytes:
        objects = ctx["objects"]
        target_os = ctx["target_os"]
        return my_link_objects(objects, target_os)

asmpython.linker.Linker(name="my_linker", impl=MyLinker())

The two built-in linkers are builtin (the x86-64 backend's own from-scratch PE/ELF linker, no external toolchain involved) and gcc (shells out to a real gcc/ld). See Backends: legacy & x86-64 for how backend and linker selection interact, and asmpython.mlang for a case that currently requires --linker gcc.

asmpython.extend #

asmpython.extend.Extension(...) registers a compiler-syntax extension: a new statement-prefix keyword handled by your own parser callback. Unlike backend/linker, an extension plugin is typically loaded straight from a file via --ext, rather than imported as an installed package. This section covers the registration API for writing your own — for the built-in extensions that ship with the compiler (constants, access, immutable, final, sealed, exhaustive_switch, enum), see the extension catalog.

python
# my_plugin.py
import asmpython

def handle_let(parser, pos):
    """`let NAME = value` -- a trivial single-binding alternative to `=`."""
    from asmpython._compiler import ast_nodes as A

    name = parser._expect("NAME").value
    parser._expect("OP", "=")
    value = parser._parse_expr()
    parser._expect("NEWLINE")
    return A.Assign(target=name, value=value, pos=pos)

asmpython.extend.Extension(id="let_binding", statement_handlers={"let": handle_let})
shell
asmpython build myfile.py --ext my_plugin.py

--ext accepts either a bare registered id (e.g. the built-in constants) or a filesystem path — a path is exec'd first (under the host CPython interpreter, never compiled by asmpython itself), registering whatever Extension(...) calls it makes, before activation by id proceeds as usual. A plugin file that registers zero or more than one Extension is a build-time error, since there'd be no unambiguous id for --ext to activate.

Constructor

ParameterDefaultMeaning
id—The name --ext and other extensions' requires/conflicts refer to this extension by
version"1.0"Dotted version string, compared as a plain tuple of ints
requires{}dict[str, str] — other extension id → minimum version that must already be active
conflictsset()Other extension ids that can't be active at the same time as this one
statement_handlers{}dict[str, Callable] — contextual keyword → handler; empty makes a metadata-only extension (useful purely as a dependency/conflict marker)

Statement-handler contract

Each statement_handlers value is a callable (parser, pos) -> ast_nodes.Stmt. parser is the live asmpython._compiler.parser.Parser instance, already positioned just past the claimed keyword — the callback drives it directly via its private _eat/_check/ _expect/_parse_expr/etc. methods and constructs a real node from asmpython._compiler.ast_nodes (a private module — there is no separate public AST surface yet, so this is the de facto contract for now).

Once an extension is active, its claimed keyword unconditionally becomes a statement prefix for the rest of that compile — unlike built-in soft keywords (const, match), there is no shape lookahead a generic third-party callback could replicate. The keyword can no longer double as a plain identifier for that build. This only ever applies when the invoker explicitly opted in via --ext.

Built-in extension: constants

The only extension asmpython ships is constants, activated with --ext constants, which adds a const NAME [: annotation] = value module-scope-only declaration that locks the name against every later rebinding form (plain reassignment, augmented assignment, del, tuple/list destructuring, walrus targets, except ... as, shadowing imports). Mutating an object a const name refers to is unaffected — only rebinding the name itself is rejected:

python
const values = [1, 2]
values.append(3)   # allowed -- rebinding `values` itself is not
values = []         # E081: cannot reassign const 'values'

There is no in-source activation directive — an earlier design used extend/retract statements for per-file activation; this was removed in favor of CLI-only activation, so a program's grammar is never a function of anything the program's own source controls. See docs/EXTENSIONS.md in the repository for the full extension-system design notes (contextual-keyword parsing, module isolation, IR/backend neutrality, security posture for third-party extensions).
