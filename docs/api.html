Public API #

The compiled language asmpython accepts is plain Python (see CPython docs). This page is about a different surface: the real Python package you pip install and import on the host interpreter to write build tooling — custom codegen backends and custom linkers. None of this executes inside a compiled asmpython program; it all runs under ordinary CPython, as part of driving a build.

The public surface is namespaced, not flat:

python
import asmpython

asmpython.backend.Backend(name="my_backend", impl=my_backend_impl)
asmpython.linker.Linker(name="my_linker", impl=my_linker_impl)
There is no flat asmpython.Backend / asmpython.linker.Linker shorthand and no backwards-compatibility alias for one — asmpython.backend and asmpython.linker are the only public entry points, each a separate submodule imported lazily so a plain import asmpython doesn't pull in the whole compiler frontend. (A third submodule, asmpython.extend, registered opt-in compiler-syntax extensions — a new statement-level keyword handled by your own parser callback. It has been withdrawn: asmpython's goal is mirroring CPython's language with only tiny, necessary differences, and letting the grammar itself be extended cut against that. The withdrawn implementation is preserved for reference under archived/extensions/ in the source tree, not part of the public API anymore.)

Both follow the same shape: construct the class, and registration happens immediately as a side effect — there's no separate .register() call. Each registered thing becomes selectable from the CLI (--backend NAME, --linker NAME) on any later asmpython build invocation in that process.

asmpython.backend

Register a full codegen backend — something that turns a compiled module into object bytes and links them. See below.

asmpython.linker

Register just a linker, reusable by any backend that wants it. See below.

asmpython.backend #

asmpython.backend.Backend(name, impl) registers a codegen backend, selectable via --backend name.

python
import asmpython

backend = asmpython.backend
backend.Backend(name="my_backend", impl=my_backend_impl)

Then: asmpython build myfile.py --backend my_backend.

The impl contract

impl must conform to asmpython._compiler.ir.IRBackend:

MemberRequiredSignature
compileyes(module, args) -> dict[str, bytes]
linkyes(objects, args) -> dict[str, bytes]
requested_argsnolist[dict] — extra CLI args your backend wants parsed and forwarded
default_linkernostr — linker name used when --linker is omitted

A registered backend is driven with a plain compile-then-link-then-write sequence (the same shape the built-in ternary backend uses) — it does not get the bespoke per-backend wiring that x86-64 has (Win64/SysV ABI shims, runtime object linking, gcc resolution for asmpython.mlang). If your backend needs that kind of target-specific plumbing, you provide it yourself inside compile/link.

Minimal example

python
import asmpython

class MyBackend:
    default_linker = "builtin"

    def compile(self, module, args) -> dict:
        # module: the compiler's typed AST/IR handoff object
        # args:   dict of target_os / abi / any requested_args
        obj_bytes = my_codegen(module, args)
        return {"main": obj_bytes}

    def link(self, objects, args) -> dict:
        exe_bytes = my_link(objects, args)
        return {"out": exe_bytes}

asmpython.backend.Backend(name="my_backend", impl=MyBackend())
Backend/linker registries are plain in-process Python dicts, consulted after the built-in names (legacy/x86-64/ternary). They're CPython-hosted-compilation only and not yet safe under self-hosting — asmpython's self-hosted subset has no first-class module/object values it could store a live backend object in.

asmpython.linker #

asmpython.linker.Linker(name, impl) registers a linker, selectable via --linker name — usable independently of any custom backend, including with the built-in x86-64 backend.

python
import asmpython

linker = asmpython.linker
linker.Linker(name="my_linker", impl=my_linker_impl)

Then: asmpython build myfile.py --linker my_linker.

The impl contract

MemberRequiredSignature
linkyes(ctx: dict) -> bytes
requested_argsnolist[dict]

ctx carries at minimum objects (a list of object-file bytes to link) and target_os.

Minimal example

python
import asmpython

class MyLinker:
    def link(self, ctx: dict) -> bytes:
        objects = ctx["objects"]
        target_os = ctx["target_os"]
        return my_link_objects(objects, target_os)

asmpython.linker.Linker(name="my_linker", impl=MyLinker())

The two built-in linkers are builtin (the x86-64 backend's own from-scratch PE/ELF linker, no external toolchain involved) and gcc (shells out to a real gcc/ld). See Backends: legacy & x86-64 for how backend and linker selection interact, and asmpython.mlang for a case that currently requires --linker gcc.

asmpython.extend (withdrawn) #

asmpython.extend.Extension(...) used to register a compiler-syntax extension: a new statement-prefix keyword handled by your own parser callback, activated per build via --ext. It has been withdrawn — asmpython's goal is mirroring CPython's language with only tiny, necessary differences, and letting the grammar itself be extended by any plugin (or by any of the 16 built-in extensions this compiler previously shipped: constants, enum, access, immutable, final, sealed, exhaustive_switch, readonly_params, const_params, no_global_mutation, no_shadowing, must_use, no_implicit_any, interface, assign_decorators, overload) cut directly against that. --ext/--apm's extension-registration surface no longer exists on the CLI, and asmpython.extend is no longer part of the public API — import asmpython.extend now fails.

The withdrawn implementation — registry, activation/retraction, conflict/dependency checking, all 16 built-in extensions, and this plugin-authoring API — is preserved as-is under archived/extensions/ in the source tree, for reference only. Nothing there is wired up to the compiler anymore; ordinary Python source (no --ext flag needed, since it doesn't exist) is the only thing asmpython compiles.
