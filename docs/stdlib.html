Built-in mlang configs #

The full asmpython.mlang writeup — Code, Config, signature inference, the linker requirement — lives on Assembly & FFI. This section is a quick reference for the ready-made Configs the compiler ships, so you don't need to read the whole page to check what's built in.

ConfigCompilerFrontendinfer_signatures
ml.builtins.gcc.cppg++ on PATH"cpp"True
ml.builtins.gcc.cgcc on PATH"c"True
 
python
import asmpython.mlang as ml

code = ml.Code(ml.builtins.gcc.cpp, 'extern "C" int add(int a, int b) { return a + b; }')
print(code.add(1, 2))   # 3

Both built-ins opt into signature inference, so a plain top-level TYPE NAME(TYPE, ...) { ... } function needs no explicit exports=. For any other compiler (Rust, a cross-compiler, a non-default C++ standard), build a ml.Config(...) of your own — see Assembly & FFI for the full field reference and worked examples.

Every mlang build currently needs --linker gcc (auto-selected once a Code(...) is detected). See the linker-requirement note for why.

Compiler extension catalog #

Extensions add opt-in syntax or extra compile-time checks that don't exist in plain Python — activated per compile with --ext NAME (one flag per extension, repeatable), never by anything in the source itself. Activation is whole-invocation: every module a build compiles (including everything a whole-program build merges in) sees the same set of active extensions. An unrecognized --ext value, or extension syntax used without its flag, is a precise compile error rather than a silent no-op or a confusing generic parse failure.

bash
python -m asmpython program.py --ext constants --ext access --ext final

Two extensions can declare themselves incompatible (final and sealed conflict — see below); activating both in one invocation is a compile error, checked before any source is parsed.

constants

Locked, non-reassignable module-level bindings.

python
const MAX_RETRIES = 5
const LABEL: str = "build"

const NAME [: annotation] = value, module scope only, initializer mandatory. Once declared, the name can never be rebound, augmented (+=), deleted, or re-targeted by any assignment form — enforced across every rebinding shape (plain assignment, tuple/starred unpacking, for targets, with...as, except...as, import aliasing, del). A const value otherwise behaves exactly like an ordinary variable of the same type — mutating a const-bound list's contents is fine; only rebinding the name itself is rejected.

access

@private / @protected modifiers on class methods and fields, checked at every call/read/write site.

python
class Account:
    @private
    def _raw_balance(self) -> int:
        return self.balance

    def get_balance(self) -> int:
        return self._raw_balance()   # fine: called from Account's own method

@private restricts a member to that exact class's own methods — not even a subclass may call it. @protected allows the declaring class and any subclass. No decorator means public (the default). Applies to both methods and class-body fields (a field needs its own decorator line, e.g. @private on its own line above balance: int).

immutable

@immutable on a class or an individual field, writable only from inside the declaring class's own __init__.

python
@immutable
class Point:
    def __init__(self, x: int, y: int) -> None:
        self.x = x    # fine: inside __init__
        self.y = y

# p = Point(3, 4); p.x = 9   -> compile error

@immutable on the class freezes every field; on an individual class-body field it freezes just that one. Either form allows normal reads everywhere — only writes outside the declaring __init__ are rejected.

final

final class forbids all subclassing; @final on a method forbids overriding it in any subclass.

python
final class Point:
    ...

class Base:
    @final
    def core(self) -> int: ...

final class is a statement prefix (a new soft keyword, like const), not a decorator — it reads more naturally attached to the class line itself than to @final, since it restricts the class as a whole rather than one member. Method finality is checked against the full ancestor chain, so re-overriding two levels down a hierarchy is still caught. Conflicts with sealed (see below).

sealed

sealed class Name(permits=A, B): — like final, but with an explicit allow-list instead of forbidding all subclasses.

python
sealed class Shape(permits=Circle, Square):
    ...

class Circle(Shape): ...
class Square(Shape): ...
# class Triangle(Shape): ...   -> compile error, not in the permits list

Conflicts with final: a class can't sensibly be both unconditionally non-subclassable and subclassable-by-an-explicit-list — a sealed class with an empty permits list is already equivalent to final, so there's no expressive gap from disallowing both together.

exhaustive_switch

Requires every match statement to end in an unguarded case _:, so a value that reaches none of the earlier cases is never silently ignored.

python
match shape:
    case Circle(r): ...
    case Square(s): ...
    case _: ...          # required when exhaustive_switch is active

No new syntax — match/case is unchanged. Without this extension, a match that hits no case simply does nothing at runtime (matching CPython's own semantics); with it active, that shape is rejected at compile time instead. A guarded trailing case (case _ if cond:) doesn't satisfy the requirement, since the guard can still fall through to no match.

enum

enum NAME: blocks of tagged, statically-typed compile-time int constants — not CPython's runtime enum.Enum class.

python
enum Color:
    RED
    GREEN
    BLUE

print(Color.RED)          # 0
print(Color.GREEN)        # 1 (auto-increments)

enum Status:
    OK = 10
    ERROR = 20   # explicit values are fine too

A bare member name auto-increments from the previous member's value (starting at 0), matching CPython's own Enum/auto() numbering; NAME = N sets an explicit value. Module scope only. Color.RED-style reads resolve entirely at compile time to a plain int — enum introduces no new runtime type — but comparing members of two different enums (Color.RED == Direction.NORTH) is still a compile error, since asmpython tracks which enum each member came from even though both sides are plain ints underneath.
