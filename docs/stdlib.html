Built-in mlang configs #

The full asmpython.mlang writeup — Code, Config, signature inference, the linker requirement — lives on Assembly & FFI. This section is a quick reference for the ready-made Configs the compiler ships, so you don't need to read the whole page to check what's built in.

ConfigCompilerFrontendinfer_signatures
ml.builtins.gcc.cppg++ on PATH"cpp"True
ml.builtins.gcc.cgcc on PATH"c"True
ml.builtins.rustrustc on PATH"rust"True
ml.builtins.nasm.win64nasm on PATH, -f win64"asm"False
ml.builtins.nasm.elf64nasm on PATH, -f elf64"asm"False
 
python
import asmpython.mlang as ml

code = ml.Code(ml.builtins.gcc.cpp, 'extern "C" int add(int a, int b) { return a + b; }')
print(code.add(1, 2))   # 3

gcc/rust opt into signature inference: a plain top-level TYPE NAME(TYPE, ...) { ... } function (C/C++) or #[no_mangle] pub extern "C" fn NAME(...) -> TYPE { ... } function (Rust) needs no explicit exports=. Raw NASM has no function-signature syntax to infer from at all, so both nasm.* configs always require an explicit exports= mapping:

python
import asmpython.mlang as ml
from asmpython.mlang import Sig

code = ml.Code(
    ml.builtins.nasm.win64,
    '''
    global subtract
    section .text
    subtract:
        mov eax, ecx
        sub eax, edx
        ret
    ''',
    exports={"subtract": Sig(["int", "int"], "int")},
)
print(code.subtract(50, 8))   # 42

There is no single ml.builtins.nasm — NASM's object format is a real target choice (-f win64 vs -f elf64 are non-interchangeable), and Config/Code resolve fully at compile time with no notion of the build's eventual target OS. Pick the one matching your --target.

For any other compiler (a cross-compiler, a non-default C++ standard, a language not listed here), build a ml.Config(...) of your own — see Assembly & FFI for the full field reference and worked examples.

Every mlang build currently needs --linker gcc (auto-selected once a Code(...) is detected). See the linker-requirement note for why.

Not built in: C# and Java

Both were investigated and deliberately left out — a real architecture gap, not an oversight. Neither language's ordinary compiler (csc/javac) produces native machine code at all (both target a managed runtime), so ahead-of-time native compilation is the only route that could work with mlang's model at all:

  • Java (GraalVM native-image): confirmed via its own --help-extra that there is no flag stopping short of a final, fully linked executable or shared library — no intermediate object file exists for mlang to extract at all.
  • C# (.NET Native AOT, dotnet publish -p:PublishAot=true): does leave a real linkable .obj behind, confirmed by a real test build — but that object depends on roughly 15 of the AOT runtime's own MSVC-format static libraries (GC, PInvoke thunks, exception handling). Linking those against asmpython's actual toolchain (GNU ld, via both --linker gcc and asmpython's own from-scratch --linker builtin) was tested directly and fails with real symbol-resolution errors — MSVC-produced .lib archives and GNU binutils don't reliably interoperate. The only linker that reliably links this object is real MSVC link.exe, which asmpython has no wrapper for today. Adding one (a new --linker msvc backend) is a legitimate, scoped follow-up, not attempted here.

Compiler extension catalog (withdrawn) #

asmpython previously shipped 16 opt-in compiler-syntax extensions (constants, access, immutable, final, sealed, exhaustive_switch, enum, and nine more added in a later wave — readonly_params, const_params, no_global_mutation, no_shadowing, must_use, no_implicit_any, interface, assign_decorators, overload), each adding opt-in syntax or extra compile-time checks that don't exist in plain Python, activated per compile via --ext NAME.

The system has been withdrawn. asmpython's goal is mirroring CPython's language with only tiny, necessary differences — a growing catalog of new keywords, decorators, and semantics Python itself doesn't have cut directly against that. --ext no longer exists as a CLI flag; none of the syntax documented in this section can be activated anymore. The implementation is preserved as-is under archived/extensions/ in the source tree, for reference only. See asmpython.extend for the equivalent note on the plugin-authoring API side.
