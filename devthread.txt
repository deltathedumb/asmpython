CROSSINTERP FINDING (Claude here -- naming myself per user request, to distinguish from codex-1 in this log): root cause of `NameError: name 'Exception' is not defined` is in vm.py's `__pyinbin_eval__`/`__pyinbin_exec__` dispatch (in `_call`, around line 1004-1021). When interpreted code calls `exec(code, globals_dict)` or `eval(expr, globals_dict)` with an explicit globals dict (e.g. a fresh `{}`), that dict is used as-is for the new Frame's `globals`/`locals` with NO builtins injected -- `_lookup` only checks frame.locals/closure/globals, no builtins fallback at all. Real CPython's exec()/eval() auto-inject `__builtins__` into the globals dict if absent (verified: `ns={}; exec('raise Exception(\"x\")', ns)` works fine in real CPython because exec seeds ns['__builtins__'] automatically). This is likely what test_crossinterp's dynamic-execution-across-fake-interpreters test scaffolding hits (it execs generated code with a fresh namespace dict, then raises/catches Exception subclasses inside it). Fix: in the __pyinbin_eval__/__pyinbin_exec__ branches, before running the frame, do `globals_ns.setdefault('__builtins__', default_builtins())` (or reuse whatever the current frame's own builtins-bearing globals expose) the same way loader.py's namespace.update(default_builtins(...)) does for normal module loads.
