Architecture & pipeline #

asmpython compiles through a shared front end and then one of two back ends. All builds go through the same first three passes:

  1. Lex (lexer.py) — tokenizes source; handles all Python literal types, f-strings, indentation blocks
  2. Parse (parser.py) — recursive-descent parser builds an AST (ast_nodes.py); inlines closures via free-variable lifting; resolves generators into state machines
  3. Sema (sema.py) — type inference and semantic analysis; resolves method overloads, propagates element types, desugars match/case, with statements, properties, and comprehensions

After sema, the typed AST hands off to whichever backend --backend selects (or its target-dependent default — see Backends: legacy & x86-64, below):

  • legacy — codegen.py walks the AST directly and emits NASM text, handed to nasm and then gcc/ld
  • x86-64 — ir_lower.py lowers the AST to a typed SSA IR, which asmpython/_backends/x86_64/ compiles straight to a relocatable object file (no assembler invocation at all) and links via the builtin PE/ELF linker or gcc

Whole-program compilation: all source files (including stdlib modules) are merged into a single compilation unit before sema. The first definition of any name wins, so stdlib can be overridden by user code.

Type system: structural, not nominal. Types flow from annotations and literals. Unannotated parameters are inferred from call sites. Class inheritance is tracked for virtual dispatch and isinstance.

Runtime: a set of hand-written helper routines (string ops, allocation, dict/list operations, exception propagation, dynamic dispatch) linked alongside your compiled code on every backend. The legacy backend emits these as NASM (inlined per-binary with --onefile, the default, or linked from a pre-built archive with --use-runtime-lib); the x86-64 backend links a precompiled runtime object directly.

Backends: legacy & x86-64 #

asmpython ships two production codegen backends, selectable with --backend legacy / --backend x86-64 (a third, ternary, is a toy balanced-ternary demo backend, and third parties can register more via asmpython.backend.Backend).

--backend legacy

The original pipeline: codegen.py walks the typed AST directly and emits NASM assembly text, which is handed to nasm to assemble and then gcc/ld to link. Supports every target, including freestanding/freestanding16 — the only backend that does, since the x86-64 IR backend has no bare-metal lowering yet. Also the only backend with @assembly_func support (see Inline assembly), since it has a real raw-NASM escape hatch that a direct-to-object pipeline doesn't.

--backend x86-64

The newer pipeline: ir_lower.py lowers the typed AST to a real SSA intermediate representation (ir.py), which asmpython/_backends/x86_64/ runs through phi elimination, linear-scan register allocation, and direct machine-code emission — producing a relocatable object file with no assembler invocation at all. Currently supports windows/linux only. Links via the backend's own builtin PE/ELF linker by default, or gcc if requested/required.

Default selection

Which backend runs when --backend is omitted depends on the target:

Target(s)Default backendWhy
windows / linux (alone or combined)x86-64Has reached strong parity with the legacy pipeline for these targets and produces smaller, faster-to-build output with no nasm/assembler step
freestanding / freestanding16 (alone or combined with anything else)legacyThe x86-64 backend has no bare-metal lowering yet; a mixed target set (e.g. --target windows,freestanding in one invocation) can't have two different auto-picked backends applied to it, so the whole build falls back to legacy rather than arbitrarily picking one target's default

Pass --backend explicitly to override either default — for example to force --backend legacy on a windows/linux build that needs @assembly_func.

Linker selection

--linker chooses how the backend's output object(s) become a final binary: builtin (the x86-64 backend's own from-scratch PE/ELF linker — its default, no external toolchain involved) or gcc (shells out to a real gcc/ ld). The legacy backend only supports --linker gcc. Third parties can register more via asmpython.linker.Linker.

asmpython.mlang currently forces --linker gcc (auto-selected when an mlang.Code(...) is detected, unless overridden) — the builtin linker's COFF parser doesn't yet understand the "bigobj" object format real g++/gcc output produces on Windows.
